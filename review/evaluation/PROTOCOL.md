# 실제 사용자·검색 평가 실행 자료

이 자료는 **실험 전 계획과 빈 양식**이다. 참가자 모집·측정·사람 데이터 승인 완료 기록이 아니다. 현재 카탈로그는 prototype이므로 공식 사실·대표 선정·관계의 사람 검수를 먼저 끝낸다. 승인된 동일 배치로 사용자·검색·성능·장애 평가를 수행하고, 평가 중 데이터가 바뀌면 배치별로 구분해 다시 측정한다.

## 사용자 비교

공대 학생 8명 이상이 동일 기기에서 같은 과제를 두 뷰로 수행한다. 슬롯 S01–S04는 2D→3D, S05–S08은 3D→2D다. 슬롯은 실제 참가자가 아니며, 참여 시 익명 코드만 부여한다. 순서별 결과도 따로 보고해 반복 학습 효과를 확인한다. 기기·브라우저·화면 크기·네트워크 조건과 배치 버전은 공통 실행 기록에 남긴다.

각 뷰를 처음 보기 상태에서 시작하고 과제 A, B를 같은 순서로 수행한다. 진행자는 정답·특정 자원명을 먼저 알려주지 않는다. 도움 요청과 완료 실패는 성공으로 고치지 않고 별도 코드로 기록한다. 탐색 과제는 AI를 기본 해제하며, AI 선택의 이해 여부는 별도 확인한다.

| 과제 | 참가자에게 읽어줄 내용 | 완료 판정 |
| --- | --- | --- |
| A · 발견과 출처 | 물과 환경을 다루는 프로젝트를 준비합니다. 도움이 될 연구실이나 교수를 하나 찾아 공식 소개를 열어 주세요. | 실제 관련 Resource를 선택하고 그 자원의 공식 Source를 열었는지 관찰한다. 시작부터 원문 열기까지 시간을 잰다. 120초 이내 여부를 별도 기록한다. |
| B · 관계 이해 | 초저온 전자현미경 관련 장비를 찾아, 공식 설치실로 연결된 공간을 확인하고 연결의 근거를 열어 주세요. | 장비→설치실 경로와 그 관계의 Source를 확인한다. 단순히 화면상 가까운 공간을 고르면 실패다. 이용·예약 가능 여부를 추정하면 성공 판정을 보류한다. |

각 뷰에서 A의 성공 여부·완료 초·120초 내 원문 확인, B의 관계 이해·근거 확인 여부를 기록한다. 미완료 시간은 null로 남긴다. 완료자의 중앙값과 실패 수를 함께 보고하고, 한 뷰에서 완료자가 없으면 시간 비교는 미완료다. 피로·멀미가 반복 보고됐는지는 익명 요약으로 기록하며 참여자는 언제든 중단할 수 있다.

`sessions.example.json`의 results는 비어 있다. 실제 결과는 별도 파일에 기록한다. 이름·학번·연락처·자유롭게 입력한 목표 원문·외부 페이지의 개인 연락처는 수집하지 않는다. 원문 열기 증거는 해당 배치의 source ID로 기록한다. 실패 원인은 `not_found`, `wrong_relation`, `source_not_opened`, `needed_help`, `label_overlap`, `slow_graph`, `stopped` 같은 코드로 남긴다.

## 검색 평가

`search-cases.json`은 학과별 1개씩의 최초 과제다. 출시 평가 전에 사람이 과제 난이도와 학과 범위를 검수하고, 승인된 자원·출처로 관련성 기준을 만든다. 아래 query는 고정 평가용 문구이며 실제 사용자 목표 로그가 아니다. AI 평가는 계정·무료 한도 검증과 외부 처리 안내·명시적 동의가 끝난 경우에만 별도로 실행한다.

모든 후보를 가능한 범위에서 두 검수자가 독립적으로 관련/무관/판정 불가로 분류한다. 각 판정에는 resource ID와 해당 주장을 지지하는 source ID를 붙인다. 이름이나 학과가 같다는 이유만으로 관련으로 세지 않는다. 의견이 다르면 공식 연구 분야·능력·장비 설명을 함께 확인해 합의한다. 판정 불가와 출처 없는 후보는 관련으로 세지 않는다.

상위 10개 중 관련 자원이 3개 이상인 과제를 통과로 센다. 결과가 10개보다 적으면 실제 반환 목록에서 센다. 카탈로그에 관련 자원이 3개 미만이면 데이터 커버리지 미달로 남기고, 과제를 삭제하거나 쉬운 이름 검색으로 바꿔 통과율을 높이지 않는다. 12개 과제를 평가하면 최소 10개가 통과해야 80% 기준을 만족한다. 자원 종류별·학과별 실패도 함께 남긴다.

## 성능·장애와 집계

승인 배치를 사용하는 실제 배포 환경에서 일반 검색 요청의 소요 시간을 모아 p95를 구한다. 첫 지도는 페이지 시작부터 이동·확대·선택이 가능한 시점까지 측정한다. 실제 데스크톱 3D에서 조작 중 프레임률을 측정하며 기기·도구·표본 수·조건을 기록한다. 로컬 빌드 시간이나 테스트 성공을 1초·3초·30fps 달성의 증거로 사용하지 않는다.

키보드, 44px 터치 타깃, 모바일, reduced motion, API 장애 시 스냅샷, AI 미동의·한도·시간 초과, WebGL 손실을 같은 배치로 확인한다. 운영 환경의 백업 복원과 이전 승인 배치 롤백은 별도로 실제 수행한다.

실측이 모두 준비되면 `infra/launch-evidence.example.json` 형식으로 `data/launch-evidence.json`을 사람이 작성한다. 집계는 다음을 따른다.

- participants: 두 뷰 비교에 실제 참여한 익명 학생 수. 슬롯 수가 아니다.
- success2d/success3d: 각 뷰에서 과제 A를 완료한 참가자 수. 과제 B의 결과는 별도 실행 기록에 첨부한다.
- medianSeconds2d/3d: 과제 A 완료자 시간 중앙값. 실패·중단 수를 함께 검토하고 완료자가 없는 뷰는 값을 만들어 넣지 않는다.
- 기본 뷰: 성공률 차이 10%p 초과, 시간 20% 초과, 반복 피로 보고 기준을 `infra/launch.ts`의 defaultView로 판정한다.
- foundAndOpenedInTwoMinutes: 결정된 기본 뷰에서 A를 120초 안에 완료한 실제 참가자 수. 8명이면 최소 7명이 필요하다.
- searchTargets/relevantTopTenPass: 학과별 실제 평가 과제 수와 그중 상위 10개에 관련 자원 3개 이상인 과제 수. 공용 시설 그룹을 학과 수로 세지 않는다.
- 나머지 성능·접근성·계정·장애·복구 항목: 같은 실행 기록으로 확인한 값만 반영한다. 비어 있는 값·실패·미수행을 true로 바꾸지 않는다.

`node --import tsx infra/release.ts data/public-snapshot.json data/launch-evidence.json`으로 최종 게이트를 확인한다. 실제 학생 결과·사람 승인·계정 또는 운영 검증이 없으면 출시 미완료를 유지한다.

## 실제 캠퍼스 개선의 추가 과제

과제 A의 성공은 관련 자원을 찾은 뒤 그 자원의 공식 위치 근거가 있는 실제 건물을 선택하고 공식 출처를 여는 것까지 포함한다. 위치 미확인 자원만 찾은 경우 목록 탐색 성공은 별도 기록하되 실제 건물 발견 성공으로 세지 않는다. `foundBuildingAndOpenedInTwoMinutes`에는 해당 완료를 120초 안에 수행한 인원만 넣는다. 8명이면 최소 7명이 필요하다.

과제 B 이후 같은 화면에서 ① 두 건물이 가까움 ② 같은 검색 주제에 해당 ③ 공식 지도교수/장비 설치 관계가 확인됨의 의미를 각각 설명하도록 요청한다. 세 구분을 모두 정확히 설명한 사람만 `relationshipMeaningCorrect`에 포함한다. 90% 이상이 필요하며 참가자가 8명이면 8명 전원이 충족해야 한다. 지리적 근접이나 주제 일치만으로 협업을 설명하면 실패로 기록한다.

연구 `batchVersion`과 `spatialBatchVersion`을 함께 기록하고 과제에 사용한 건물 ID, 위치 근거 source ID, 관계 source ID를 남긴다. 개인 연락처 노출·미확인 동명이인 병합·출처 없는 관계 건수는 실제 점검 결과가 0인 경우만 각각 0으로 제출한다. 점검 전 빈 값을 0으로 채우지 않는다.

공식 건물 목록의 각 건물은 표시·좌표만 표시·윤곽 미확인·미수록과 그 사유를 대조한다. 정밀 지면고도·실측 건물 높이·실내 좌표를 개략 표현과 혼동하는지도 관찰한다. 모바일은 같은 공간 배치의 2D를 기본 제공하고 3D 전환과 뷰·건물·자원·지도 시점 공유 복원을 검증한다.

## 실제 결과 묶음과 판정 검증 도구

2026-10-27 초안의 실제 일반 검색 상위 10개와 자원·정보별 출처·확인된 위치·관계는 `campus-search-candidates-20261027.json`에 고정했다. `campus-reviews.pending.json`에는 사람 판정이 없으므로 `campus-search-pending-report.json`의 `evaluationConducted`는 false다. 후보 수가 3개 미만인 과제는 데이터·검색 보강 대상으로 남긴다. 실제 관련도나 학생 성공률은 이 후보 수로 계산하지 않는다.

Node.js 24에서 새 묶음은 다음과 같이 생성한다. 출력 파일은 이미 존재하면 덮어쓰지 않는다.

```sh
node --import tsx infra/search-evaluation-cli.ts export data/college-draft.json data/campus/campus-draft.json data/coverage/coverage-draft.json review/evaluation/search-cases.json /tmp/new-candidates.json
```

검수 파일은 `{ "exportedAt": "내보낸 checkedAt", "reviews": { "candidateSha256": "내보낸 해시", "batchVersion": "연구 버전", "spatialBatchVersion": "공간 버전", "reviews": [] } }` 구조다. 각 검수는 `caseId`, 개인 연락처가 아닌 `reviewerId`, `checkedAt`, `judgments`를 담는다. 각 판정에는 실제 상위 결과의 `resourceId`, `relevant`, 해당 결과에 딸린 `sourceIds`, `reason`이 필요하다. 실제 반환한 결과를 빠짐없이 한 번씩 판정한다. 과제마다 서로 다른 두 검수자가 필요하며, 의견이 다르면 관련으로 세지 않는다. 빈 결과도 두 검수자가 확인할 수 있으며 통과로 세지 않는다.

```sh
node --import tsx infra/search-evaluation-cli.ts score data/college-draft.json data/campus/campus-draft.json data/coverage/coverage-draft.json review/evaluation/search-cases.json /tmp/new-score.json /tmp/completed-reviews.json
```

집계 시 현재 코드로 같은 시점·과제의 결과를 재생성하고 내용 해시를 대조한다. 같은 일자 버전이라도 결과·출처·관계·위치·과제가 달라졌으면 과거 판정을 재사용하지 않는다. 동일 검수자 중복, 누락 판정, 모르는 자원·출처, 시점 역전, 다른 배치는 거부한다. 이 도구는 출시 승인이나 8명 학생 평가를 대신하지 않는다.

2026-10-27 표현 보완 후의 최신 후보 묶음은 `campus-search-candidates-variants-20261027.json`, 빈 검수 양식은 `campus-variant-reviews.pending.json`, 미수행 집계는 `campus-variant-search-pending-report.json`이다. 앞선 파일은 보완 전 기준 기록으로 보존한다. 기존 명시 검색 표현 목록에 이상치/이상 탐지와 유연/flexible을 추가하고 원문 일치를 우선했다. flexible은 영어 단어 경계를 확인한다. 10개 과제에서 후보 3개 이상이 반환되지만 실제 관련도 통과가 아니다. 검색 결과 내용 해시가 달라지므로 이전 묶음의 판정을 새 결과에 재사용할 수 없다.
